# Buzzer App – Product Requirements Document (PRD)

## 1. Overview

A real‑time buzzer application (similar to Jackbox) where a host creates a room, players join via QR code or 6‑character code, and buzz in response to prompts. The host sees all buzzers reorder in real time, can skip incorrect buzzes, and advance rounds. Built as a Progressive Web App (PWA) for cross‑platform use, with **no login required**.

**Primary goal:** Portfolio piece for junior/mid‑level roles, demonstrating real‑time architecture, database design, PWAs, and clean UX.

**Deployment:** Angular PWA → Netlify (static hosting, HTTPS).  
**Backend & real‑time:** Supabase (PostgreSQL + WebSocket subscriptions, free tier).  
**No physical server** – cloud only, though the design could be self‑hosted on a Raspberry Pi.

## 3. Database Schema (Supabase PostgreSQL)

### 3.1 Rooms table

    CREATE TABLE rooms (
      id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
      code TEXT UNIQUE NOT NULL DEFAULT generate_room_code(),
      host_token UUID NOT NULL UNIQUE,
      current_round INTEGER NOT NULL DEFAULT 1,
      round_active BOOLEAN DEFAULT FALSE,
      hostless_mode BOOLEAN DEFAULT FALSE,
      created_at TIMESTAMPTZ DEFAULT now()
    );

**Room code generator (PostgreSQL function):**

    CREATE OR REPLACE FUNCTION generate_room_code()
    RETURNS TEXT AS $$
    DECLARE
      chars TEXT[] := ARRAY['A','B','C','D','E','F','G','H','J','K','M','N','P','Q','R','S','T','U','V','W','X','Y','Z','2','3','4','5','6','7','8','9'];
      result TEXT := '';
      i INT;
    BEGIN
      FOR i IN 1..6 LOOP
        result := result || chars[1 + floor(random() * array_length(chars, 1))];
      END LOOP;
      RETURN result;
    END;
    $$ LANGUAGE plpgsql;

### 3.2 Players table

    CREATE TABLE players (
      id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
      room_id UUID REFERENCES rooms(id) ON DELETE CASCADE,
      name TEXT NOT NULL,
      player_token UUID DEFAULT gen_random_uuid(),
      is_active BOOLEAN DEFAULT TRUE,
      joined_at TIMESTAMPTZ DEFAULT now()
    );

### 3.3 Buzzes table

    CREATE TABLE buzzes (
      id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
      room_id UUID REFERENCES rooms(id) ON DELETE CASCADE,
      player_id UUID REFERENCES players(id) ON DELETE CASCADE,
      round_number INTEGER NOT NULL,
      buzzed_at TIMESTAMPTZ DEFAULT now(),
      buzz_order BIGSERIAL NOT NULL,
      is_skipped BOOLEAN DEFAULT FALSE
    );

    CREATE INDEX idx_buzzes_room_round_order ON buzzes(room_id, round_number, buzz_order);

### 3.4 Row Level Security (RLS) – simplified

- `rooms`: `SELECT` allowed for everyone; `UPDATE` allowed only if the request includes the matching `host_token` (checked via `WHERE` clause in application layer – no formal RLS needed for MVP).
- `players`: `INSERT` allowed; `SELECT` allowed for own player or host (through room membership).
- `buzzes`: `INSERT` allowed for players in the room; `UPDATE` allowed only for host (using `host_token` in the `WHERE` clause of the update statement).

**No authentication required** – players are anonymous; host token secures admin actions.

## 4. Core Flows

### 4.1 Host creates a room
1. Host visits `/host` -> clicks “Create Room”.
2. Angular calls Supabase: `INSERT INTO rooms (host_token) VALUES (uuid_generate_v4()) RETURNING *`.
3. Room is created; `code` auto‑generated by DB.
4. Host stores `host_token` and `room_id` in `localStorage`.
5. Host is navigated to `/room/:roomId?host=true`.
6. QR code (of join URL + code) displayed for others.

### 4.2 Player joins a room
1. Player scans QR code or navigates to `/join` and enters 6‑char code.
2. Angular fetches room by `code`. If room exists, player enters a name.
3. Call `INSERT INTO players (room_id, name)` – returns `player_token`.
4. Player token stored in `localStorage` (scoped to that `room_id`).
5. Player subscribes to real‑time updates for that room (buzzes, round state).

**Re‑joining:** If player closes browser and returns, the stored token is sent to Supabase to reclaim the same player record (if still active and room exists).

### 4.3 Buzzing (with optimistic UI)
1. Player clicks “BUZZ” button.
2. Optimistically show “You buzzed!” and temporarily disable button.
3. Send insert to `buzzes` table:
   `{ room_id, player_id, round_number: currentRound }`
4. On success, show “Buzzed #” (buzz_order).  
   On failure (e.g., round ended), show error and re‑enable button.

### 4.4 Host real‑time control panel
- Host subscribes to `buzzes` table (filtered by `room_id` and `round_number`).
- Host sees a grid of all players who buzzed, ordered by `buzz_order ASC`.
- **Reordering:** Whenever a new buzz arrives or `is_skipped` toggles, the list automatically reorders (Angular `async` pipe + `trackBy`).
- **Highlighting:** The first not‑skipped buzzer is visually emphasised (e.g., gold border, larger box).

### 4.5 Host actions
- **Skip (incorrect):**  
  Click “Skip” on a buzzer →  
  `UPDATE buzzes SET is_skipped = true WHERE id = ? AND room_id IN (SELECT id FROM rooms WHERE host_token = ?)`.  
  Real‑time update reorders list; next buzzer becomes first.
- **Next round:**  
  Click “Next Round” →  
  `UPDATE rooms SET current_round = current_round + 1, round_active = false WHERE host_token = ?`.  
  (New round requires host to click “Start Round” to set `round_active = true`.)
- **Start round:**  
  `UPDATE rooms SET round_active = true WHERE host_token = ?`.

### 4.6 PWA installability
- `manifest.json` with `start_url`, `display: standalone`, icons.
- Service worker (AngularPWA) caches static shell only – no background sync, no push notifications.

## 5. Security & Access Control

| Action                     | Protection                                                                 |
|----------------------------|-----------------------------------------------------------------------------|
| Create room                | Public (anyone can be host). Host token generated on server.               |
| Update `buzzes.is_skipped` | SQL `WHERE` clause checks that `room_id` belongs to room with `host_token`.|
| Update `rooms.current_round`| Same host token check.                                                     |
| Player re‑join             | Player token stored in `localStorage` must match `players.player_token`.   |
| XSS / token leakage        | Strict Content Security Policy (CSP), avoid `innerHTML`.                   |

---

## 6. Risks & Mitigations

| Risk                                 | Mitigation                                                                 |
|--------------------------------------|-----------------------------------------------------------------------------|
| **Race condition on buzz insert**    | Use `BIGSERIAL` (auto‑incrementing sequence) for strict ordering, not just timestamps. |
| **Real‑time subscription flooding UI**| Angular `trackBy` + `ChangeDetectionStrategy.OnPush` + debounce rapid re‑renders (but Supabase batches). |
| **Host token stored in localStorage**| CSP headers to reduce XSS risk; token only used for writes, not reads.     |
| **QR code / deep linking fails**     | Angular routing with route param for `roomId` and `?join=true`; on init, fetch room and join using stored/local token. |
| **Supabase free tier limits**         | Rooms limited to small concurrent usage (typical for portfolio). Logs monitored. |

## 8. Development Roadmap (MVP)

1. **Setup** – Angular project + PWA, Netlify deploy preview, Supabase project.
2. **Database** – create tables, indexes, room code function, RLS (optional).
3. **Create room flow** – API call, store token, display room code + QR.
4. **Join flow** – code entry, name input, store player token, subscribe to room state.
5. **Buzz action** – insert buzz, optimistic UI, handle errors.
6. **Host control panel** – real‑time list of buzzers, ordering, skip button, next round button.
7. **PWA polish** – manifest, service worker, install prompt.
8. **Testing** – simulate multiple clients (different browsers/incognito).
9. **Deploy** – Netlify production with environment variables (Supabase URL + anon key).
